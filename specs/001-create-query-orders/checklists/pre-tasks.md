## HTTP Contract Completeness and Clarity

- [x] CHK001 ¿Está reconciliado explícitamente que existen dos capacidades de negocio —crear y consultar por identificador— pero tres operaciones HTTP al incluir `GET /orders`, y usa cada artefacto la misma convención para contar rutas, operaciones y capacidades? [Consistency, Conflict, Spec §Scope/FR-001/FR-015, Plan §Technical Context/Scale-Scope, Research §2, OpenAPI §paths]
  - **Resuelto**: `spec.md` §Scope, `plan.md` §Capabilities and HTTP operations, `research.md` §2 y las tres operaciones de OpenAPI usan la misma terminología.
- [x] CHK002 ¿Está definido de forma inequívoca que `GET /orders` sólo representa la ausencia de `orderId`, devuelve `400` y nunca lista ni busca órdenes, mientras `GET /orders/{orderId}` realiza la única consulta de negocio y distingue `400` de `404`? [Clarity, Spec §FR-018/FR-019, Plan §Design/Request flow, Research §2, OpenAPI §paths./orders.get/paths./orders~1{orderId}.get]
  - **Resuelto**: `spec.md` FR-018/FR-019, `plan.md` §Query request flow y ambas operaciones OpenAPI cierran `400`/`404` y prohíben listado.
- [x] CHK003 ¿El contrato de `POST /orders` especifica el tratamiento de propiedades ausentes, nulas, adicionales o repetidas, elementos nulos, cuerpo ausente y `Content-Type` ausente o no soportado, sin dejar esas decisiones al comportamiento predeterminado del framework? [Completeness, Gap, Spec §FR-001–FR-008, Research §8/§9, OpenAPI §CreateOrderRequest/OrderItemInput]
  - **Resuelto**: `plan.md` §JSON policy, `research.md` §3, `data-model.md` §Transport input y OpenAPI documentan cada caso y la configuración nativa explícita.
- [x] CHK004 ¿Los contratos de éxito fijan de manera cerrada los campos permitidos, su nulabilidad, media type y semántica, incluidos el `Location` relativo de `201`, el estado `Pending` y la ausencia de semántica en el orden de `items`? [Completeness, Consistency, Spec §FR-011–FR-017/SR-004, Data Model §Order/Relationships, OpenAPI §responses.201/responses.200]
  - **Resuelto**: OpenAPI usa schemas de éxito `additionalProperties: false`, required no nulos, media types y `Location` pattern; `data-model.md` §Relationships niega semántica posicional.
- [x] CHK005 ¿Existe una matriz completa y deliberada de respuestas por operación que cubra o excluya expresamente `400`, `404`, `405`, `408` o timeout equivalente, `413`, `415`, `500` y `503`, con media type y esquema para cada fallo aplicable? [Completeness, Gap, Spec §FR-008/FR-018/FR-019/SR-005, Plan §Validation and errors, Research §9, OpenAPI §paths]
  - **Resuelto**: `plan.md` §Normative response matrix, `research.md` §10 y OpenAPI cubren respuestas aplicables; `405`, timeout, routing y disconnect se excluyen del contrato Problem Details.
- [x] CHK006 ¿Está precisado cómo se interpreta un `orderId` opaco al cruzar el routing HTTP —decodificación porcentual, whitespace, slash codificado, Unicode, trailing slash y coincidencia ordinal— y qué casos son `400`, `404` o no alcanzan la operación? [Clarity, Ambiguity, Spec §Edge Cases/FR-015/FR-019, Plan §Design/Request flow, Research §5, OpenAPI §paths./orders~1{orderId}.get]
  - **Resuelto con límite explícito**: `plan.md` §Query request flow y OpenAPI garantizan la ruta `Location` UUID ASCII, blanco `400`, valor alcanzado no coincidente `404` y comparación ordinal; slash/encoding/segmentos que no enruta el host quedan fuera de la operación y de Problem Details.
- [x] CHK007 ¿Está diferenciada de forma normativa la cantidad positiva sin máximo de negocio de su representación técnica `Int64`, incluidos los valores JSON matemáticamente enteros, notación exponencial, fracciones y valores fuera de rango? [Clarity, Ambiguity, Spec §FR-005/FR-021, Plan §Constraints, Research §8, Data Model §OrderItem, OpenAPI §OrderItemInput.quantity]
  - **Resuelto**: `spec.md` FR-005/FR-021, `plan.md` §JSON policy, `research.md` §3 y OpenAPI rechazan fracción/exponente/overflow y separan Int64 del límite HTTP.
- [x] CHK008 ¿Está definido un catálogo normativo y estable de Problem Details por clase de fallo —`type`, `title`, `status`, `detail`, `instance`, `traceId` y claves de `errors`— en vez de depender sólo de ejemplos parciales? [Completeness, Verifiability, Gap, Spec §FR-008/FR-018/FR-019/SR-005, Plan §Validation and errors, Research §9, OpenAPI §Problem/ValidationProblem]
  - **Resuelto**: `plan.md` §Application Problem Details catalog fija vocabulario/campos/keys y OpenAPI define schemas cerrados y enums aplicables.

- [x] CHK011 ¿Está definido el resultado observable y el estado persistente para fallos en cada frontera —espera del escritor, apertura, insert de orden, insert de item, constraint, commit, cancelación y fallo al enviar la respuesta después del commit— sin estados de creación “desconocidos”? - [x] CHK012 ¿Están documentadas las decisiones operativas necesarias de SQLite —inicialización y validación de esquema, `foreign_keys`, WAL, `STRICT`, nivel de aislamiento, `busy_timeout` y política de sincronización/durabilidad— junto con el requisito o riesgo que justifica cada una? - [x] CHK013 ¿La garantía de unicidad de `orderId` define de forma completa la generación UUID v4, el formato canónico, la restricción definitiva, el alcance temporal de unicidad, el número o presupuesto de reintentos ante colisión y el resultado terminal si no se obtiene un ID nuevo? [Coverage, Gap, Spec §Clarifications/FR-009, Plan §Constraints, Research §5/§7, Data Model §Uniqueness under concurrency, OpenAPI §paths./orders.post]
  - **Resuelto**: `spec.md` Approved Decisions/FR-009, `plan.md` §Atomicity, `research.md` §6, data model y POST OpenAPI distinguen `503` probado de resultados inciertos y prohíben idempotency key.
- [x] CHK015 ¿Las reglas de producto duplicado precisan comparación ordinal exacta, diferencias de case/whitespace/Unicode, varios duplicados distintos, tres o más repeticiones y la interacción con `productId` nulos o inválidos, además de cómo se informa cada duplicado? ## Concurrency and Operational Limits

- [x] CHK017 ¿Está especificada la semántica de una lectura que compite con una creación antes, durante y después del commit, incluidos snapshot visible, ausencia de lecturas parciales y resultado permitido si la consulta llega antes de que la creación se confirme? [Coverage, Gap, Spec §FR-014–FR-018, Plan §Persistence and concurrency, Research §6/§7, Data Model §Atomic creation invariant]
  - **Resuelto**: `spec.md` Approved Decisions, `plan.md` §Concurrency, `research.md` §7 y `data-model.md` §Concurrency fijan snapshot anterior/`404`, sin parciales y disponibilidad post-commit.
- [x] CHK018 ¿La restricción a una instancia y un archivo local está declarada como supuesto operativo vinculante, y está claro qué garantías dependen del `SemaphoreSlim` de proceso y cuáles permanecen protegidas por SQLite si aparece otro proceso? [Clarity, Assumption, Plan §Target Platform/Constraints/Scale-Scope, Research §4/§7]
  - **Resuelto**: `plan.md` §Concurrency guarantees y `research.md` §7 asignan serialización/timeout al gate y ACID/constraints/locks/snapshot a SQLite; multi-process queda no soportado.
- [x] CHK019 ¿Está definido el comportamiento de la cola de escritores bajo 25 solicitudes concurrentes —capacidad, espera máxima, cancelación, equidad o riesgo aceptado de starvation— con un criterio que separe operación normal de saturación? [Completeness, Gap, Spec §FR-020/SC-006, Plan §Persistence and concurrency, Research §7/§12]
  - **Resuelto**: `plan.md` §Concurrency y `research.md` §7 declaran espera async, sin cola adicional/FIFO, 1 segundo, cancelación pre-transacción y riesgo de starvation aceptado; load target exige cero `503`.
- [x] CHK020 ¿Cada timeout relevante tiene un valor exacto, punto de inicio y presupuesto coherente —espera del gate, lock/busy de SQLite, transacción y solicitud HTTP— de modo que “inferior a 2 segundos” no obligue al implementador a inventar umbrales? [Clarity, Measurability, Gap, Spec §SC-006, Plan §Persistence and concurrency, Research §7]
  - **Resuelto**: `plan.md` §Concurrency budgets y `research.md` §7 fijan 1.000 ms gate + 500 ms busy + 500 ms margen, ausencia deliberada de timeout transaccional/server y 5 s sólo como fail-safe del harness.
- [x] CHK021 ¿Los disparadores de `503` distinguen saturación del gate, lock/busy, almacenamiento no disponible, error transitorio y error permanente, y definen garantía de no commit, posibilidad de retry y presencia o ausencia deliberada de `Retry-After`? [Completeness, Gap, Plan §Persistence and concurrency/Validation and errors, Research §7/§9, OpenAPI §responses.503]
  - **Resuelto**: `plan.md` §503 taxonomy, `research.md` §11 y OpenAPI restringen `503` pre-commit, separan `500`, explican retry/uncertainty y omiten `Retry-After`.
- [x] CHK022 ¿El `413` fija el límite exacto en bytes, el componente que lo aplica, si mide cuerpo codificado o descomprimido, cómo trata `Content-Length` ausente o engañoso y si Problem Details está garantizado aun cuando el host rechaza antes del endpoint? [Clarity, Measurability, Gap, Spec §FR-021, Research §9, OpenAPI §paths./orders.post.responses.413]
  - **Resuelto**: `research.md` §9, `plan.md` §Create flow, quickstart HostBoundary y OpenAPI fijan Kestrel 1.048.576 bytes, sin decompression, Content-Length/chunked, no truncamiento y no garantía de Problem Details.
- [x] CHK023 ¿Existe una taxonomía consistente que separe máximos de negocio, rango representacional `Int64`, límite de transporte, capacidad de concurrencia, timeout y recursos físicos, manteniendo rechazo explícito, total y sin truncamiento en cada caso? [Consistency, Ambiguity, Spec §FR-005/FR-008/FR-021, Plan §Constraints, Research §7–§9, OpenAPI §OrderItemInput/responses.413/responses.503]
  - **Resuelto**: `spec.md` FR-005/FR-021, `plan.md` Constraints/JSON/503 y `research.md` §§3,7,9,11 separan las seis clases y su rechazo.
- [x] CHK024 ¿El criterio de 25 usuarios es reproducible porque documenta mezcla exacta de operaciones, solicitudes por usuario, sincronización inicial, iteraciones, warm-up, tamaño/estado de base, entorno de ejecución, aislamiento de carga, ventana de medición y algoritmo de p95? [Measurability, Verifiability, Gap, Spec §SC-006, Plan §Performance Goals, Research §10/§12]
  - **Resuelto**: `research.md` §14 y `quickstart.md` §SC-006 fijan warm-up DB separada, 25 seeds, 25 usuarios, cinco ciclos barrera, 500 ops 25/75, entorno, ventana y nearest-rank.
