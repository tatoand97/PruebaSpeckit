# Pre-Tasks Technical Requirements & Design Quality Checklist: Creación y consulta de órdenes

**Purpose**: Evaluar si los requisitos y las decisiones de diseño están completos, claros, consistentes, medibles, verificables y suficientemente precisos para autorizar `/speckit-tasks`
**Created**: 2026-07-28
**Feature**: [spec.md](../spec.md)

**Note**: Este checklist evalúa exclusivamente la calidad documental de `spec.md`, `plan.md`, `research.md`, `data-model.md` y `contracts/openapi.yaml`; no contiene pruebas ni verificaciones de implementación.

## HTTP Contract Completeness and Clarity

- [ ] CHK001 ¿Está reconciliado explícitamente que existen dos capacidades de negocio —crear y consultar por identificador— pero tres operaciones HTTP al incluir `GET /orders`, y usa cada artefacto la misma convención para contar rutas, operaciones y capacidades? [Consistency, Conflict, Spec §Scope/FR-001/FR-015, Plan §Technical Context/Scale-Scope, Research §2, OpenAPI §paths]
- [ ] CHK002 ¿Está definido de forma inequívoca que `GET /orders` sólo representa la ausencia de `orderId`, devuelve `400` y nunca lista ni busca órdenes, mientras `GET /orders/{orderId}` realiza la única consulta de negocio y distingue `400` de `404`? [Clarity, Spec §FR-018/FR-019, Plan §Design/Request flow, Research §2, OpenAPI §paths./orders.get/paths./orders~1{orderId}.get]
- [ ] CHK003 ¿El contrato de `POST /orders` especifica el tratamiento de propiedades ausentes, nulas, adicionales o repetidas, elementos nulos, cuerpo ausente y `Content-Type` ausente o no soportado, sin dejar esas decisiones al comportamiento predeterminado del framework? [Completeness, Gap, Spec §FR-001–FR-008, Research §8/§9, OpenAPI §CreateOrderRequest/OrderItemInput]
- [ ] CHK004 ¿Los contratos de éxito fijan de manera cerrada los campos permitidos, su nulabilidad, media type y semántica, incluidos el `Location` relativo de `201`, el estado `Pending` y la ausencia de semántica en el orden de `items`? [Completeness, Consistency, Spec §FR-011–FR-017/SR-004, Data Model §Order/Relationships, OpenAPI §responses.201/responses.200]
- [ ] CHK005 ¿Existe una matriz completa y deliberada de respuestas por operación que cubra o excluya expresamente `400`, `404`, `405`, `408` o timeout equivalente, `413`, `415`, `500` y `503`, con media type y esquema para cada fallo aplicable? [Completeness, Gap, Spec §FR-008/FR-018/FR-019/SR-005, Plan §Validation and errors, Research §9, OpenAPI §paths]
- [ ] CHK006 ¿Está precisado cómo se interpreta un `orderId` opaco al cruzar el routing HTTP —decodificación porcentual, whitespace, slash codificado, Unicode, trailing slash y coincidencia ordinal— y qué casos son `400`, `404` o no alcanzan la operación? [Clarity, Ambiguity, Spec §Edge Cases/FR-015/FR-019, Plan §Design/Request flow, Research §5, OpenAPI §paths./orders~1{orderId}.get]
- [ ] CHK007 ¿Está diferenciada de forma normativa la cantidad positiva sin máximo de negocio de su representación técnica `Int64`, incluidos los valores JSON matemáticamente enteros, notación exponencial, fracciones y valores fuera de rango? [Clarity, Ambiguity, Spec §FR-005/FR-021, Plan §Constraints, Research §8, Data Model §OrderItem, OpenAPI §OrderItemInput.quantity]
- [ ] CHK008 ¿Está definido un catálogo normativo y estable de Problem Details por clase de fallo —`type`, `title`, `status`, `detail`, `instance`, `traceId` y claves de `errors`— en vez de depender sólo de ejemplos parciales? [Completeness, Verifiability, Gap, Spec §FR-008/FR-018/FR-019/SR-005, Plan §Validation and errors, Research §9, OpenAPI §Problem/ValidationProblem]

## Persistence, Atomicity, and Identity

- [ ] CHK009 ¿La expresión “durante la vida útil de la PoC” define una frontera de durabilidad verificable frente a reinicio del proceso, reinicio del host, cierre inesperado, recreación del entorno y pérdida o reemplazo del archivo de datos? [Clarity, Ambiguity, Spec §FR-014/Assumptions, Plan §Storage, Research §4]
- [ ] CHK010 ¿La creación atómica está descrita consistentemente como validación completa previa, una única transacción para `orders` y todos los `order_items`, commit anterior a `201` y ausencia de cualquier estado consultable parcial? [Completeness, Consistency, Spec §FR-007–FR-009/Edge Cases, Plan §Design/Persistence and concurrency, Research §6, Data Model §Atomic creation invariant]
- [ ] CHK011 ¿Está definido el resultado observable y el estado persistente para fallos en cada frontera —espera del escritor, apertura, insert de orden, insert de item, constraint, commit, cancelación y fallo al enviar la respuesta después del commit— sin estados de creación “desconocidos”? [Coverage, Gap, Spec §FR-007–FR-009/FR-014, Plan §Design/Request flow, Research §6/§7, Data Model §Atomic creation invariant, OpenAPI §responses.201/responses.503]
- [ ] CHK012 ¿Están documentadas las decisiones operativas necesarias de SQLite —inicialización y validación de esquema, `foreign_keys`, WAL, `STRICT`, nivel de aislamiento, `busy_timeout` y política de sincronización/durabilidad— junto con el requisito o riesgo que justifica cada una? [Completeness, Traceability, Gap, Plan §Storage/Design, Research §4/§6/§7, Data Model §Relational mapping]
- [ ] CHK013 ¿La garantía de unicidad de `orderId` define de forma completa la generación UUID v4, el formato canónico, la restricción definitiva, el alcance temporal de unicidad, el número o presupuesto de reintentos ante colisión y el resultado terminal si no se obtiene un ID nuevo? [Completeness, Gap, Spec §FR-010/FR-020/SR-003, Plan §Design/Request flow, Research §5, Data Model §Identity/Uniqueness under concurrency, OpenAPI §CreateOrderResponse.orderId]
- [ ] CHK014 ¿La ausencia deliberada de idempotencia está documentada con sus consecuencias para reenvíos, reintentos tras `503`, timeout o desconexión con resultado incierto, y deja claro cuándo un retry puede crear otra orden? [Coverage, Gap, Spec §Clarifications/FR-009, Plan §Constraints, Research §5/§7, Data Model §Uniqueness under concurrency, OpenAPI §paths./orders.post]
- [ ] CHK015 ¿Las reglas de producto duplicado precisan comparación ordinal exacta, diferencias de case/whitespace/Unicode, varios duplicados distintos, tres o más repeticiones y la interacción con `productId` nulos o inválidos, además de cómo se informa cada duplicado? [Clarity, Ambiguity, Spec §FR-003/FR-006/FR-008, Research §8, Data Model §Validation invariants, OpenAPI §ValidationProblem]
- [ ] CHK016 ¿La conservación exacta de identificadores y cantidades, la igualdad binaria en persistencia y la decisión de que el orden de `items` no tenga semántica están alineadas sin pérdida de información entre requisito, modelo y contrato? [Consistency, Spec §FR-015–FR-017/Edge Cases, Plan §Validation and errors, Research §8, Data Model §Relationships, OpenAPI §OrderResponse]

## Concurrency and Operational Limits

- [ ] CHK017 ¿Está especificada la semántica de una lectura que compite con una creación antes, durante y después del commit, incluidos snapshot visible, ausencia de lecturas parciales y resultado permitido si la consulta llega antes de que la creación se confirme? [Coverage, Gap, Spec §FR-014–FR-018, Plan §Persistence and concurrency, Research §6/§7, Data Model §Atomic creation invariant]
- [ ] CHK018 ¿La restricción a una instancia y un archivo local está declarada como supuesto operativo vinculante, y está claro qué garantías dependen del `SemaphoreSlim` de proceso y cuáles permanecen protegidas por SQLite si aparece otro proceso? [Clarity, Assumption, Plan §Target Platform/Constraints/Scale-Scope, Research §4/§7]
- [ ] CHK019 ¿Está definido el comportamiento de la cola de escritores bajo 25 solicitudes concurrentes —capacidad, espera máxima, cancelación, equidad o riesgo aceptado de starvation— con un criterio que separe operación normal de saturación? [Completeness, Gap, Spec §FR-020/SC-006, Plan §Persistence and concurrency, Research §7/§12]
- [ ] CHK020 ¿Cada timeout relevante tiene un valor exacto, punto de inicio y presupuesto coherente —espera del gate, lock/busy de SQLite, transacción y solicitud HTTP— de modo que “inferior a 2 segundos” no obligue al implementador a inventar umbrales? [Clarity, Measurability, Gap, Spec §SC-006, Plan §Persistence and concurrency, Research §7]
- [ ] CHK021 ¿Los disparadores de `503` distinguen saturación del gate, lock/busy, almacenamiento no disponible, error transitorio y error permanente, y definen garantía de no commit, posibilidad de retry y presencia o ausencia deliberada de `Retry-After`? [Completeness, Gap, Plan §Persistence and concurrency/Validation and errors, Research §7/§9, OpenAPI §responses.503]
- [ ] CHK022 ¿El `413` fija el límite exacto en bytes, el componente que lo aplica, si mide cuerpo codificado o descomprimido, cómo trata `Content-Length` ausente o engañoso y si Problem Details está garantizado aun cuando el host rechaza antes del endpoint? [Clarity, Measurability, Gap, Spec §FR-021, Research §9, OpenAPI §paths./orders.post.responses.413]
- [ ] CHK023 ¿Existe una taxonomía consistente que separe máximos de negocio, rango representacional `Int64`, límite de transporte, capacidad de concurrencia, timeout y recursos físicos, manteniendo rechazo explícito, total y sin truncamiento en cada caso? [Consistency, Ambiguity, Spec §FR-005/FR-008/FR-021, Plan §Constraints, Research §7–§9, OpenAPI §OrderItemInput/responses.413/responses.503]
- [ ] CHK024 ¿El criterio de 25 usuarios es reproducible porque documenta mezcla exacta de operaciones, solicitudes por usuario, sincronización inicial, iteraciones, warm-up, tamaño/estado de base, entorno de ejecución, aislamiento de carga, ventana de medición y algoritmo de p95? [Measurability, Verifiability, Gap, Spec §SC-006, Plan §Performance Goals, Research §10/§12]

## Error Handling, Security, and Privacy

- [ ] CHK025 ¿Los criterios medibles cubren la obligación de acumular “todas las reglas incumplidas detectadas” y no sólo el criterio más débil de comunicar “al menos una razón”, indicando qué errores pueden coexistir y cuáles no pueden detectarse tras un fallo de parsing? [Consistency, Measurability, Gap, Spec §FR-008/SC-002, Research §8, OpenAPI §ValidationProblem]
- [ ] CHK026 ¿Están cubiertos de manera deliberada cuerpo ausente, JSON truncado o malformado, tipos incorrectos, número fuera de rango, media type incorrecto, campos desconocidos o repetidos y colecciones o elementos nulos, con una clasificación estable de error? [Coverage, Gap, Spec §Edge Cases/SR-001, Research §8/§9, OpenAPI §paths./orders.post]
- [ ] CHK027 ¿Los fallos inesperados, de arranque/esquema, filesystem, permisos, corrupción y almacenamiento lleno tienen clasificación HTTP y Problem Details documentada, o están excluidos explícitamente con una razón? [Coverage, Gap, Spec §SR-005, Plan §Security/Observability, Research §4/§9/§11, OpenAPI §paths]
- [ ] CHK028 ¿Los requisitos de error prohíben stack traces, SQL, rutas y datos ajenos, y además limitan y escapan cualquier eco de entrada —por ejemplo el `productId` duplicado— para evitar revelar o amplificar contenido controlado por el solicitante? [Security, Privacy, Gap, Spec §FR-006/SR-005/SR-007, Plan §Validation and errors, Research §9/§11, OpenAPI §duplicateProduct]
- [ ] CHK029 ¿La ausencia de autenticación y autorización está expresada como restricción deliberada de PoC con una definición verificable de “entorno controlado”, superficie de red permitida, uso de HTTP/TLS y responsable de impedir exposición fuera de ese límite? [Security, Clarity, Ambiguity, Spec §Scope/SR-002/Assumptions, Plan §Security/Target Platform, Research §2, OpenAPI §info/servers]
- [ ] CHK030 ¿SC-007 define cómo se clasifica y evidencia que el 100 % de los datos es sintético o no sensible, incluidos identificadores que puedan llegar en requests, errores, evidencias de aceptación y archivos SQLite? [Security, Privacy, Measurability, Gap, Spec §SR-002/SR-006/SC-007, Plan §Security]
- [ ] CHK031 ¿La exigencia de exponer únicamente los datos de la orden solicitada está reflejada de forma verificable en esquemas que aclaran la política de propiedades adicionales y extensiones tanto para éxitos como para errores? [Consistency, Security, Gap, Spec §FR-016/SR-004, Data Model §Order, OpenAPI §OrderResponse/Problem/ValidationProblem]
- [ ] CHK032 ¿La política de logging enumera exhaustivamente datos prohibidos y permitidos —orderId, customerId, productId, cuerpos, headers, query/path crudo, connection string, ruta del archivo, SQL, parámetros y excepciones— para que la redacción “sin contenido sensible” no requiera interpretación? [Completeness, Privacy, Gap, Spec §SR-007, Plan §Security/Observability, Research §11]
- [ ] CHK033 ¿La ausencia o presencia de rate limiting, cuotas y protección frente a abuso está decidida y trazada explícitamente considerando una API sin autenticación, identificadores opacos sin máximos de negocio y el límite objetivo de 25 usuarios? [Security, Operational Limits, Gap, Spec §FR-021/SR-002, Plan §Constraints/Security, Research §7/§12]
